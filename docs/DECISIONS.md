- **D-20 · Civil vs military airspace ids.** `AirspaceZone` has no purpose field, so civil air routes are `DANGER` zones with ids `Z-CIV-nn` (avoid while active) and military transit strips are `CORRIDOR` zones with ids `Z-MIL-nn` (usable). - **D-25 · Base site rules.** Sites are arbitrary points in the INDIA_CONTEXT boxes (not real installations). - **D-36 · D-18..D-20 additive schema changes kept; D-22 (map boundaries) deferred to Phase 6.**
- **D-37 · Fusion is computed on read.** There is no persisted "fused" table. `ingest/service.py` loads the stored scenario rows, builds the adapters, applies pins and fuses, deterministically. Fusion time is `t0 + now_min` (query parameter, default 0), so staleness can be shown advancing with the simulated clock. `state_version` is the number of pins written for the scenario (monotonic).
- **D-38 · The fused snapshot includes a noisy secondary source by default.** BUILD_PLAN asks for a second, noisy synthetic source "for some fields". `SecondarySyntheticAdapter` is derived from the same scenario and seed (so it is deterministic), covers about half the records, perturbs a documented list of fields (`NOISE` in `ingest/adapters/synthetic.py`: aircraft status/fuel/hours/availability, crew status/duty, weapon qty, threat severity/radius/centre, airspace end time, weather visibility/ceiling/wind; never mission requests) and gives about a quarter of its reports a stale timestamp. It is synthetic by construction and is not a model of any real second system. `GET snapshot` and `fusion-report` use it unless `secondary=false`; `fused=false` returns the stored scenario exactly. Placeholder numbers: trust SYNTHETIC 1.0, SYNTHETIC_SECONDARY 0.7, FILE:* 0.8, OPEN_METEO 0.9; max age aircraft 60, crew 120, weapon stock 240, missions 1440, threats 30, airspace 360, weather 180 min; tau = max age; numbers differ materially beyond 5% (lat/lon: 0.02 degrees). The report echoes this config with a "configuration, not empirical" notice. Phase 3 decides which snapshot (fused or stored) the planners consume.
- **D-39 · Per-record provenance means one source wins a whole record.** Entities carry one `Provenance` each, so every field of a record has the same age, trust and confidence per source; the same source therefore wins all fields of a record, and only a human pin can split winners within a record. Conflicts are still reported per field (only fields that differ materially). Fused record provenance: `source` = source that won most fields, `observed_at` = oldest winning observation, `confidence` = lowest winning confidence, `data_label` = external if any winner is external, else synthetic if any winner is synthetic, else open (never labels synthetic data as real). Record `staleness_min` = oldest winning observation; `stale_fields` lists fields whose winner is stale.
- **D-40 · Stale-but-SERVICEABLE is handled by a helper, not by rewriting data.** `ingest.fusion.effective_aircraft_status()` returns DEGRADED when the status field's winning observation is stale and the stored status is SERVICEABLE (ALGORITHMS §1.4). Phase 3 `risk.py` is expected to use it; the fused entity keeps the reported value.
- **D-41 · Pins and the audit log.** A pin is stored append-only (`fusion_pin` table, newest wins) and is audited (`audit/log.py`, entries `au_00001...` per scenario, no update/delete function). The pin API accepts a source's value or an explicit value; the pinned record is re-validated against the entity schema in a dry run before anything is written (422 `invalid_pin_value`). There is no unpin endpoint (not in API_SPEC); a new pin replaces the old one and both stay in the audit log. A pin overrides all sources and counts as fresh. `GET /audit` and the WebSocket `fusion.conflict` message are Phase 5 (hub and audit endpoint not built yet).
- **D-42 · FileAdapter conventions.** CSV/JSON rows follow the entity schema; provenance comes from the adapter defaults or a row's `_observed_at` / `_confidence` / `_ingested_at` columns (underscore prefix avoids clashing with `Threat.confidence`). CSV scalars are left to schema coercion so ids like `007` keep their zeros. Bad rows are returned as `rejected` records and surface in the fusion report; an unusable file raises `AdapterError`. The API does not accept file paths for feeds (security); wiring a real feed is configuration for a later phase. The Open-Meteo weather adapter (PRD F-5) stays in Phase 7.

## Session 2 (Phase 3)

- **D-43 · What the planners read.** `planning/` is pure: a `PlanningContext` is built from a `ScenarioFile` (stored or fused) plus optional fusion metadata and a `now_min` (nothing takes off earlier). `GET /feasibility` defaults to the fused snapshot with the noisy secondary source (same defaults as `snapshot`, D-38) and offers `fused=false` / `secondary=false`. Tests and, later, benchmarks use stored scenarios. A SERVICEABLE status whose observation is stale is treated as DEGRADED (D-40).
- **D-44 · Time, geometry, approximations.** Transit = ceil(distance / cruise * 60) whole minutes; sortie = takeoff, transit, on station for the mission duration, transit back; takeoffs are multiples of 15 min. Distances are haversine (D-35). The route (base to AOI centre, loiter, back, great circles) is sampled about every 10 km and every 15 min on station; each sample knows its minute, so an airspace zone or threat only counts while it is active at that minute. Airspace uses shapely point-in-polygon on the samples. Documented limits: spherical Earth; zones narrower than the sample step can be missed; zone altitude bands are ignored (conservative); the AOI is its centre point; weather "at the target" is the nearest base's forecast (approximation); a place with no forecast is not checked. Shared primitives (`build_profile`, physics, haversine) are tested on their own.
- **D-45 · Risk (ALGORITHMS §4, refined).** Threat exposure is time-weighted: sum over active zones of severity x confidence x (flight minutes inside / total flight minutes), including time on station, so a zone on the AOI cannot hide behind a long transit. The mission's `max_acceptable_risk` is a hard limit on the **threat component only** (reason `THREAT_RISK_EXCEEDS_LIMIT`); weather risk and service risk are costs, not limits (weather minima are their own hard check). Weather and service risk are **placeholder formulas** (margin above minima and thunderstorm probability; hours since maintenance and DEGRADED status) until the Phase 7 models replace them. Total risk assumes the three risks are independent.
- **D-46 · Aircraft interpretations.** DEGRADED aircraft may fly (+0.15 service risk; `allow_degraded=False` forbids). UNSERVICEABLE / IN_MAINTENANCE aircraft return at `available_from_min` only if that is after `now_min`; otherwise they are unserviceable with no return time (so Phase 5 events should set `available_from_min` to the return time, or beyond the horizon for indefinite). `fuel_state_pct` is not used (assumed refuelled during turnaround). Diversion is covered by the 20% reserve; the alternate-airfield list is not used in planning yet. Missions with no loadout requirement use the sentinel loadout id `NONE`. A loadout too heavy for the density altitude at the base is reported as `LOADOUT_INCOMPATIBLE` (there is no payload code). Range and endurance use the generator's rule (flight minutes <= endurance x range factor x 0.8; radius derated by the same factor).
- **D-47 · Crew rules.** Only AVAILABLE crew at the aircraft's base, qualified on the type. Required roles are the type's seats plus any extra role the mission lists. Duty: `duty_minutes_last_24h` plus the sortie must fit 720 min, and rolling 24 h windows of planned sorties must too (the carried duty counts only in windows that reach back before t0). Rest: 600 min before the first sortie (from `last_duty_end_min`) and between sorties of the same crew. The 720 / 600 values are the scenario's `duty_rules` placeholders.
- **D-48 · Several aircraft per mission.** Each of the `aircraft_required` sorties independently covers the whole on-station duration inside the window; they are not synchronised into a formation (limitation). A mission is placed all-or-nothing by the baselines. Runway capacity is a placeholder: 2 takeoff-or-landing operations per runway per 15 min slot. Aircraft are busy until landing plus the base's turnaround for that type.
- **D-49 · Reason accounting and lint.** The feasibility check evaluates every constraint even after an earlier one failed, so explanations list all blockers. `blocked_by` counts aircraft options (aircraft x loadout) per code; one option can count under several codes; aircraft that cannot do the capability are not counted as blocked options (a mission-level `NO_CAPABLE_AIRCRAFT` is raised when the fleet has fewer capable aircraft than required). Resource conflicts met while placing (turnaround, stock, runway, crew) are added to the unassigned mission's reasons. `E501` is ignored in `tests/` only.
- **D-50 · Validator independence.** `validate.py` imports none of `feasibility`, `resources`, `greedy` or `risk`; it re-derives each rule from the scenario (a test enforces the import rule) and has mutation tests that break one thing at a time. It shares only low-level primitives (physics, haversine, route sampling). It also checks plan integrity (duplicate ids, partial missions, assigned-and-unassigned, frozen assignments against a parent plan).
- **D-51 · Measured, not claimed.** On the 20 seeded default scenarios, both baselines produce plans with zero violations (test), and every intentionally infeasible mission is flagged with its intended reason (test). Coverage numbers are not reported anywhere: they come from `benchmarks/` in Phase 7.
