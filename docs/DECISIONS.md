# DECISIONS

Log of defaults chosen where the specs were ambiguous, and of any deviation from the fixed stack.
Format: `D-nn · date · decision — rationale`.

## Session 1 (Phases 0–1)

- **D-01 · 2026-10-02 · Nested git repo.** `git init -b main` inside `D:\AirPower`. The enclosing `D:\` repo is a drive-wide untracked tree; commits there would be unsafe. The README also says to `git init` in the project folder.
- **D-02 · Repo root.** `CLAUDE.md` shows `airpower/` as the root; the repo root is `D:\AirPower` itself.
- **D-03 · Python environment.** Python 3.13 is installed (spec: 3.11+). Dependencies go in `backend/.venv`. `requires-python = ">=3.11"`.
- **D-04 · Storage in Phase 1.** SQLModel tables exist for every entity. Scenarios are persisted as canonical JSON files in `scenarios/` plus a lightweight registry row in SQLite, and the snapshot endpoint is served by rebuilding from the stored scenario. Full per-entity table writes and `state_version` come with the fusion layer (Phase 2).
- **D-05 · Weather in the generator.** The generator emits a synthetic hourly forecast per base (`source="SYNTHETIC"`). The real Open-Meteo adapter is Phase 7.
- **D-06 · Placeholder numbers.** All aircraft-type, loadout, crew-duty and weight numbers are illustrative placeholders. Each scenario file carries a `notes` field saying so.
- **D-07 · Compose database.** `db` is PostgreSQL; the password in `.env.example` is a placeholder. Dev uses SQLite, no Docker.
- **D-08 · Map tiles.** MapLibre with a free raster OpenStreetMap style, attribution visible. Terms check for the demo: to be re-verified before any public demo (OSM tile usage policy discourages heavy use of the public tile server); not a blocker for a local prototype.
- **D-09 · Scripts instead of Makefile.** Windows host, so `scripts/*.ps1` / plain commands in the README rather than a Makefile.
- **D-10 · Scenario JSON determinism.** Canonical form: `sort_keys=True`, 2-space indent, `ensure_ascii`, floats rounded to fixed decimals at generation time, trailing newline, LF line endings.
- **D-11 · 2026-10-02 · Windows Application Control blocks some compiled packages.** On this machine, `import sklearn` and `import pyproj` fail with "An Application Control policy has blocked this file" (unsigned `.pyd` files), and `python -m ruff` is blocked, while `.venv/Scripts/ruff.exe` run directly works. We did not attempt to bypass the policy. Phases 0–1 import neither library. Consequence for later phases: `pyproj` (Phase 3) and `scikit-learn` (Phase 7) need the user to allow these files or run in Docker/WSL. Linting here is run as `backend/.venv/Scripts/ruff.exe check .`.
- **D-12 · 2026-10-02 · Neutral map region.** Fictional bases are placed in a bounding box of lat −28…−22, lon 130…138 (sparsely populated interior), shown on open OSM tiles. This follows HONESTY.md ("fictional base names on a neutral map region") and avoids implying real military sites. The region is a presentation choice, not a claim about any real location.
- **D-13 · 2026-10-02 · MapLibre v6 worker.** `maplibre-gl` v6 has no default export and its web worker fails under Turbopack. The worker and shared chunk are copied to `frontend/public/maplibre/` by `scripts/copy-maplibre-worker.mjs` (run by `predev`/`prebuild`; the folder is git-ignored) and wired with `setWorkerUrl`. No new dependency.
- **D-14 · 2026-10-02 · Frontend scaffold choices.** Next.js 16 (App Router, Turbopack), Tailwind 4. System fonts instead of `next/font/google` to avoid a build-time network fetch. The scaffold's dark-mode CSS was removed (out of scope). Scaffold-generated `frontend/AGENTS.md` and `frontend/CLAUDE.md` are kept as generated.
- **D-15 · 2026-10-02 · Compose `db` service vs. database driver.** Compose defines a PostgreSQL `db` service as the spec requires, but the stack list contains no PostgreSQL driver (e.g. `psycopg`), and adding one needs approval. Until then the `api` service uses SQLite on a volume. Validated with `docker compose --env-file .env.example config` only; images were not built in Phases 0–1 (end-to-end compose check is Task 8.5).

## Session 2 (India context; Phase 1 continued)

- **D-16 · Supersedes D-12.** `INDIA_CONTEXT.md` overrides generic defaults. The neutral-region box is dropped; bases are fictional codenames (`BASE-N1`, `BASE-W2`, …) placed at sites inside the five India region boxes. `n_bases` is now 2–6 (was 2–3) so a scenario can span regions.
- **D-17 · Region boxes do not cover the Bay of Bengal east coast.** The five boxes (INDIA_CONTEXT §2) leave out roughly 82–87 E (Odisha / Andhra coast). I did not add a sixth region without approval. `cyclone_east_coast` therefore uses the south box (coast up to ~80 E) plus east/NE, and is named for the scenario theme, not a claim of exact coastline coverage. **Needs your call if you want a sixth region.**
- **D-18 · Schema additions, limited to what INDIA_CONTEXT names.** `Base.region/elevation_m/climate_zone` (§6) and `Base.ref_temperature_c` (§3.2 "a temperature"); `Capability.HADR`; `Mission.disaster_event` (str reference, no separate disaster entity); scenario `season_preset` and `region_mix` (§6); a new group `alternate_airfields` (§3.5). Not added: payload capacity / altitude sensitivity on `AircraftType` — they live in `core/physics.py::TYPE_PERFORMANCE` (code table) to avoid an unlisted entity change. Say so if you prefer them as entity fields.
- **D-19 · Representation choices.** `set[...]` fields from DATA_MODEL are sorted lists (hash-seed-independent JSON). The aircraft-type capability field keeps DATA_MODEL's name `role` (ALGORITHMS writes `roles`). `WeatherMinima` is embedded in `AircraftType` (per type; per-capability minima not modelled yet). `Event`, `MaintenanceRecord` and `Airfield` carry a `Provenance` block like every other record. `ScenarioMeta` gains `params`, `duty_rules`, `hard_cases` (generator ground truth for tests/benchmarks), `open_data_sources`, `notes`. Scenario `data_label` is `"mixed"` when real open airport data is included.
- **D-20 · Civil vs military airspace ids.** `AirspaceZone` has no purpose field, so civil air routes are `DANGER` zones with ids `Z-CIV-nn` (avoid while active) and military transit strips are `CORRIDOR` zones with ids `Z-MIL-nn` (usable). Other zones are `Z-nn`. Civil route *geometry* is synthetic (between real civil airport coordinates); no real airspace data is used.
- **D-21 · Amends D-04.** Phase 1 stores every group as rows (id + scenario id + JSON) in SQLite and rebuilds the snapshot from the rows, as DATA_MODEL §3 says. The generate endpoint writes to the DB only; the CLI writes JSON files. `Plan`, `Proposal` and `AuditEntry` tables exist but are unused until later phases. `POST /scenarios/load` only reads `.json` files inside `AIRPOWER_SCENARIO_DIR`. `seed` is required (no hidden default), so `AIRPOWER_DEFAULT_SEED` is removed.
- **D-22 · Map boundaries (open item, blocks the COP map).** The OSM raster basemap used in Phase 0 draws boundaries as OSM does, which does not necessarily match the Government of India depiction. The Phase 0 placeholder map stays centred outside India and shows no India overlay until Phase 6 resolves this (boundary overlay from a verified source, or a style without administrative boundaries plus a GoI layer). Licence and depiction check to be recorded in Phase 6.
- **D-23 · Density altitude.** Standard ISA approximation in `core/physics.py`, hand-checked in `tests/test_physics.py`. Per-type numbers are placeholders; labelled approximate.
- **D-24 · External data licence checks (2026-10-02), approved by you for a one-time fetch.**
  - *OurAirports* `airports.csv`: site states "All data is released to the Public Domain, and comes with no guarantee of accuracy or fitness for use." Attribution not required (given anyway). Trimmed to Indian airports with `scheduled_service=yes` (116 rows) → `backend/app/sim/data/india_airports.json`. Used only as divert/alternate candidates.
  - *Open-Meteo elevation API*: data under CC BY 4.0 (attribution required); free for non-commercial use (<10,000 calls/day); the elevation API is covered by the same terms. 40 calls' worth of points in one request → `backend/app/sim/data/sites.json`. Attribution is carried in `open_data_sources` of every scenario file and must appear in the UI/README. The prototype is non-commercial; re-check if that changes.
  - Both files are committed so generation is offline and deterministic; `scripts/fetch_open_data.py` reproduces them. Fetched copies are versioned inputs: re-fetching can change generated output.
- **D-25 · Base site rules.** Sites are arbitrary points in the INDIA_CONTEXT boxes (not real installations). Sites above 4,500 m are not eligible to host a base (no real airfield is that high); the cap is a generator constant. Added `ClimateZone.INDO_GANGETIC_PLAIN` because INDIA_CONTEXT §3.1 names the Indo-Gangetic plain in the winter-fog preset.
- **D-26 · Scenario dates.** Season preset start dates are notional and set after the open-data fetch date (monsoon 2027-07-20, pre-monsoon 2027-05-15, post-monsoon 2026-10-28, winter 2026-12-15), 02:30 UTC = 08:00 IST, so open-data provenance never post-dates the scenario.
- **D-27 · Maintenance history size.** The embedded history is 30 days × fleet by default to keep scenario files small. It is too short to train a model on; Phase 7 will call the documented hazard function (`sim/hazard.py`) to simulate a larger synthetic training set. Not a real-fleet dataset.
