# HONESTY.md — rules for data, claims and scope

This project must be defensible to evaluators. Everything below is mandatory.

## 1. Data provenance

| Kind | Allowed? | How |
|---|---|---|
| Real classified / MoD operational data | **Never** — we do not have it and must not pretend to | — |
| Synthetic data generated by our own seeded generator | Yes | Every record carries `source = "SYNTHETIC"`; UI shows a persistent "SYNTHETIC DATA" badge |
| Real open data (e.g. public weather API) | Yes | Carries its true source name, fetch time, and licence note |
| Real aircraft names/specs | Avoid | Use generic types (FTR-A, TPT-B, HEL-C, ISR-D, TKR-E). Their numbers are **illustrative placeholders**, labelled as such in `scenarios/` and the UI |
| Real bases / units / people | Avoid | Use fictional base names on a fictional or neutral map region |

## 2. Models and numbers

- Predictive models are trained on **synthetic** history produced by our generator. They demonstrate the pipeline and the integration. The UI must label them "trained on synthetic data — not validated on real fleets". Never quote their accuracy as real-world accuracy.
- Reported improvement figures (e.g. "x% more priority-weighted missions covered than greedy baseline") must be produced by `benchmarks/run_benchmarks.py` with seeds recorded, and cited as "on N synthetic scenarios". If not run: "not measured".
- Solve-time claims come from measured runs on a stated machine.

## 3. Scope boundaries

- Advisory decision support only. Human approval required for every plan change.
- No targeting, weapon-employment, or kill-chain logic. "Weapon load" is treated only as a **resource attribute** (type, count, compatibility with mission category), as in logistics.
- No claim that this is deployable by MoD/IAF. Honest framing: "a working prototype showing the architecture and algorithms such a system would use, with a pluggable adapter layer for real feeds."

## 4. Things to say in the presentation (truthful framing)

- What is real: the fusion architecture, constraint model, optimiser, retasking logic, explainability, UI, audit trail, the open-weather integration.
- What is simulated: fleet, crew, missions, threats, maintenance history.
- What would be needed for real use: security accreditation, real data-link adapters, validation against real ops, certification.

## 5. Third-party and licensing

- Use only open-source libraries with permissive/compatible licences; list them in README.
- If using map tiles, use a free/open style and keep the attribution visible.
- Verify any external API's terms before using it in the demo; record the check in `docs/DECISIONS.md`.

## 6a. India context

The project is India-specific in geography, seasons, civil airspace and mission types (see `INDIA_CONTEXT.md`). Bases, units, squadrons, tail numbers and order of battle stay fictional. Show India's boundaries per official Government of India depiction. Never imply MoD/IAF endorsement.

## 6. For Claude Code

If you are about to write a number, name, or claim that is not derived from our code or a cited open source, stop and either compute it, label it as a placeholder, or leave it out.
